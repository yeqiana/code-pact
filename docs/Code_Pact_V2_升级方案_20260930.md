# Code Pact V2 升级方案（2026）

> 日期：2026-09-30  
> 仓库：code-pact  
> 当前基线：main @ d660eaa  
> 本文档只定义升级路线，不直接修改现有 Skill、规范、Prompt 或 CI。

---

## 1. 结论

当前仓库的核心思想没有过时：小任务轻流程、大任务才增加结构、控制改动范围、必须拿验证证据、没有验证不能声称完成、最终交付保持简洁。

真正落后一代的是执行模型。V1 主要把 Coding Agent 当成一次会话里的“自动程序员”；2026 年主流实践已经转向 Context Engineering、Harness Engineering、长任务状态续接、并行 Agent、自动行为评测和 maintainer-quality 验收。

V2 不推翻 V1，建议保留约 70%~80% 现有规则，只升级以下部分：

1. 任务分级从“人类工时”转向风险与变更面。
2. Minimal Diff 升级为 Minimal Sufficient Change。
3. 增加 Context Contract。
4. 增加 Harness Contract。
5. 为 L2/L3 增加 Durable State / Resume Contract。
6. 增加 Parallelism / Delegation 判断。
7. 角色从厂商型改为能力型。
8. 人工确认边界收缩到不可逆副作用。
9. 验收从“tests pass”升级为 functional + repository + regression + maintainer-quality。
10. 行为评测从人工 8 Case 升级为可自动回归的 Eval Contract。

---

## 2. V2 定位

V2 仍然是轻量 Guardrails，不做以下事情：

- 不实现多 Agent 调度平台。
- 不实现 Workflow Engine。
- 不实现 Agent Memory 服务。
- 不实现数据库。
- 不强制引入 OpenSpec。
- 不实现 MCP Runtime。
- 不把本仓库改造成 StoryOS 一类平台。

本仓库继续只负责一件事：

> 给 Coding Agent 提供轻量、可移植、可执行、可验证的工程边界。

建议将 V2 核心拆成 10 个合同：

1. Task Complexity Contract
2. Risk Contract
3. Context Contract
4. Change Contract
5. Execution Contract
6. State / Resume Contract
7. Parallelism / Delegation Contract
8. Validation Contract
9. Human Approval Contract
10. Evaluation Contract

## 2.1 评审修正：实施时覆盖后文冲突

以下修正是本方案进入 Phase 0 / Phase 1 前的强制约束；若后文章节存在冲突，以本节为准。

### A. Normative Source 必须一次性切换

Phase 1 不允许同时存在两个 active normative source。

必须在同一个 cutover commit 内完成：

1. 新建 references/code-pact-execution-spec-v2.md，并设为唯一 active normative source。
2. references/code-pact-execution-spec-v1.md 保留为 historical baseline，并明确标记 SUPERSEDED。
3. SKILL.md 改为引用 v2。
4. README.md 与 README.zh-CN.md 改为引用 v2。
5. active behavior contracts 同步到 v2 语义。
6. scripts/test-skill.ps1 改为校验 v2 authority。
7. stable skill identifier $code-pact 不得改变。

禁止先引入 v2，再用后续提交慢慢追平其他文件。

### B. V1 Behavior Case 只冻结为历史基线，不冻结旧语义

Phase 0 要把当前 8 个 Behavior Case 原样保存为 V1 historical baseline。

其中 V1 Case 4 的旧规则是：高风险小改在 implementation 前要求 explicit scope confirmation。V2 不继续沿用这个执行语义。

V2 必须拆开两类确认：

- Scope Confirmation：只解决未决产品选择、验收标准、职责边界。
- Execution Approval：只解决不可逆或外部副作用是否真的执行。

高风险任务可以先 inspect、plan、sandbox patch、local validation；真正 irreversible / external mutation 前才必须 Execution Approval。

### C. Durable State 是触发式能力

L2/L3 只表示 eligible，不表示必须创建状态文件。

只有满足任一条件才启用 Durable State：

- 跨 session；
- background / async Job；
- Agent handoff；
- 长时间执行且上下文可能丢失；
- workspace 可能明显漂移；
- 多 Agent / 多槽位协作；
- 用户明确要求持续推进或中断续接。

一次会话即可闭环的 L2，不得为了流程完整额外创建 state artifact。

### D. Maintainer-quality Review 必须绑定仓库原生证据

Maintainer-quality Review 不得变成新的主观评分表。

必须优先引用：

- AGENTS / project instructions；
- canonical spec / architecture docs；
- existing abstractions and callers；
- linters / typecheck / tests；
- schema / API contracts；
- existing repository patterns。

禁止输出架构质量 8.5/10 一类伪精确评分。没有 repo-native evidence 的判断必须标为推断。

### E. Behavior Eval 必须定义非确定性语义

自动行为评测至少记录：

- case revision；
- repo fixture revision；
- model；
- agent/runtime version；
- skill revision；
- run count；
- pass count；
- failure reason；
- evidence。

Case 分两类：

- Deterministic Contract：每次必须 PASS。
- Behavioral Contract：允许非确定性。初始建议 critical case 3/3，普通 behavior case 至少 2/3。

跨版本 regression 禁止只看一次运行的 pass/fail。

### F. Phase 0 Compatibility Contract

Phase 0 必须冻结以下兼容接口：

- Product name = Code Pact
- Repository = code-pact
- Stable skill identifier = $code-pact

V2 不允许破坏 stable skill identifier。

### G. Phase 1 必改文件

Phase 1 的最小 authority cutover 写集至少包括：

- references/code-pact-execution-spec-v2.md
- references/code-pact-execution-spec-v1.md
- SKILL.md
- README.md
- README.zh-CN.md
- evals/behavior-contracts.md
- evals/manual-evaluation.md
- scripts/test-skill.ps1

agents/openai.yaml、prompts、examples 只有在静态合同或语义确实需要时再改。

## 3. 任务分级 V2

### 3.1 当前问题

V1 用 5~15 分钟、30 分钟~2 小时、半天~2 天、多天~多周来定义 L0/L1/L2/L3。

这在 Agent 时代不稳定：

- 人类需要两天的机械迁移，Agent 可能几十分钟完成。
- 一行 production auth 配置改动虽然很小，但风险极高。
- 30 个文件的机械修改可能很大，却高度可逆且容易验证。

### 3.2 V2 判断维度

任务等级改由以下因素决定：

| 维度 | 含义 |
| --- | --- |
| Change Surface | 涉及多少模块、接口、数据与调用方 |
| Uncertainty | 需求、现状、验收标准是否明确 |
| Blast Radius | 出错影响范围 |
| Reversibility | 是否容易撤销 |
| Validation Cost | 证明正确需要多少验证 |
| Shared-State Sensitivity | 是否影响数据库、生产配置、公共契约、共享状态 |
| Parallelizability | 是否可安全拆成独立任务 |

工时只作为辅助，不再决定等级。

### 3.3 推荐等级

L0：Local / Reversible  
局部、明确、可逆、无共享状态，流程为 inspect → change → focused validation → summary。

L1：Bounded Change  
跨少量相邻层，影响范围可枚举，可在一次任务中闭环，流程为 impact scan → minimal sufficient change → validation → summary。

L2：Cross-boundary / Risky  
涉及公共 API、auth、权限、数据库、生产配置、多模块、关键歧义、长时间运行或多阶段验证时自动升级。需要 short decision record、state artifact、分阶段验证。

L3：Architectural / Long-running  
核心架构变化、大迁移、多 Agent、长任务、大 blast radius。必须有 durable state、checkpoint、rollback/resume、完整回归和 maintainer-quality review。

## 4. Minimal Diff 升级为 Minimal Sufficient Change

V1 的“少改文件、少改代码、不顺手重构”继续保留，但不再把最小行数当最高目标。

V2 定义：

> 在满足需求、保持仓库一致性、避免重复状态源和长期架构熵的前提下，选择最小充分修改。

以下情况允许受控结构调整：

1. 局部补丁会制造第二套状态源。
2. 会复制已有 canonical logic。
3. 会绕过 canonical path。
4. 会形成长期兼容债。
5. 根因位于公共抽象而不是当前表面文件。

结构调整必须同时满足：范围明确、原因明确、有回归覆盖、不扩展到无关区域。

## 5. Context Contract

目标是避免两种极端：

- 上下文太少，Agent 靠猜。
- 上下文太多，Agent 被噪音淹没。

建议上下文加载顺序：

1. User Task
2. Repository Instructions / AGENTS / Skill
3. Canonical Spec / Contract
4. Directly Affected Code
5. Direct Tests
6. Callers / Consumers
7. Relevant Config / Schema
8. Prior Failure Evidence
9. Optional External Research

新增规则：

- 小任务禁止默认扫描整个仓库。
- 禁止默认读取所有 docs。
- 禁止默认加载所有历史记录。
- 新上下文只有在能减少不确定性或支持验证时才加入。
- Context selection 本身属于 Agent 的执行质量。

---

## 6. Harness Contract

V2 不实现 Harness Runtime，但要明确 Agent 如何使用宿主 Harness。

核心规则：

- 优先使用 repo-native tools 和项目已有命令。
- 必须读取真实执行结果。
- 测试失败后必须基于真实失败继续修复。
- 不得把“计划”写成“结果”。
- 不得把“文件生成成功”当作验证成功。
- 不得把静态 Markdown 检查当成 Agent 行为评测。
- 不得在没有实际证据时写 should work、probably fixed、merge-ready。

标准闭环：

inspect → modify → run → observe → diagnose → repair → rerun → evidence

## 7. Durable State / Resume Contract

只对 L2/L3、长任务、多 session、外部 Job、Agent handoff、持续推进任务启用。

建议最小逻辑状态：

- task_id
- goal
- scope
- last_verified_revision
- completed
- remaining
- blocked
- failed_attempts
- validation_evidence
- next_action

不强制本仓库创建固定状态目录，具体存储由宿主项目决定。

Resume 时禁止重新从头扫描整个仓库。正确顺序：

1. 读取 durable state。
2. 校验 last_verified_revision。
3. 检查 workspace drift。
4. 读取未完成项、失败尝试和验证证据。
5. 从 next_action 继续。

---

## 8. Parallelism / Delegation Contract

不默认并行。

只有同时满足以下条件才建议并行：

- 子任务输入输出清晰。
- 写文件范围基本不重叠。
- 不共享可变状态。
- 每个子任务可独立验证。
- 合并依赖清晰。

建议任务增加四类标签：

- single-agent
- parallel-safe
- delegateable
- shared-state-sensitive

并行任务应明确：

- owner
- scope
- write_set
- read_dependencies
- expected_output
- validation
- merge_dependency

本仓库只定义判断原则，不实现 Scheduler。

## 9. 角色模型从厂商型改成能力型

V1 中类似 GPT 负责分析、Codex/Claude Code 负责实现、Cursor 负责局部修改的描述应逐步废弃。

V2 改成能力角色：

- Planner
- Implementer
- Reviewer
- Validator
- Researcher
- Orchestrator

规范只描述“需要什么能力”，不绑定某一家模型、Agent 或 IDE。运行时再决定谁承担角色。

这样可以避免模型能力升级后规范迅速过时。

---

## 10. Human Approval Boundary

V2 不再因为“任务风险高”就让 Agent 在分析阶段停住。

以下行为默认可以自主进行：

- 读取
- 搜索
- 分析
- 制定方案
- sandbox 修改
- 本地测试
- dry-run
- 生成 patch
- 可逆实验

以下动作才需要强 gate：

- 数据删除
- 不可逆 migration
- 生产环境 mutation
- 对外发送
- 合并或发布
- 付费动作
- 权限扩大
- secret / credential 变更
- 用户明确要求确认的动作

原则：

> Risk controls execution side effects, not thinking and inspection.

## 11. Validation Contract V2

P0/P1/P2 分级继续保留，但 P0 不再只理解成“测试是否通过”。

V2 P0 Evidence 至少包括：

- Functional Evidence
- Repository Conformance
- Change Scope
- Regression Evidence

重要变更再增加：

- Maintainer-quality Review

新增硬规则：

> 自动测试通过，不自动等于 merge-ready。

只有以下均成立时才允许给出 merge-ready / merge candidate：

1. 核心需求已实现。
2. P0 functional validation 通过。
3. 没有未声明的 scope expansion。
4. repo conventions 没有被破坏。
5. 公共契约消费者已检查。
6. 没有新增第二状态源或明显架构熵。
7. 关键风险已有证据。

## 12. Evaluation Contract

### 12.1 当前基础

仓库已有：

- evals/behavior-contracts.md
- evals/manual-evaluation.md
- scripts/test-skill.ps1
- .github/workflows/validate.yml

这已经是良好基础，但当前 CI 主要证明“规则文本存在”，不能证明真实 Agent 行为正确。

### 12.2 V2 目标

评测体系升级为三层：

1. Static Contract Test
2. Agent Behavior Eval
3. Cross-version Regression

### 12.3 Eval Fixture

建议每个行为 Case 结构化为：

- id
- task
- repo_fixture
- expected_behaviors
- forbidden_behaviors
- required_evidence
- max_ceremony

### 12.4 第一批新增 Case

在现有 8 个 Case 基础上新增至少 8 个：

1. Minimal Sufficient Change：不能为了少改几行绕过 canonical abstraction。
2. Context Budget：小任务不能默认全仓扫描。
3. Resume：已有 checkpoint 时不得从头重做。
4. Parallel Safety：shared-state-sensitive 任务不得盲目并行。
5. Irreversible Gate：sandbox 可继续，production mutation 必须停在 gate。
6. Maintainer-quality：tests pass 但制造重复状态源时不得 merge-ready。
7. Capability Roles：不能依赖 GPT/Codex/Claude 的固定能力假设。
8. Harness Feedback：测试失败后必须根据实际错误修复，而不是只解释。

### 12.5 自动化顺序

Stage A：先做 harness-neutral fixture schema、评分标准和结果记录。

Stage B：再增加 OpenAI、Claude 等 provider adapter。

每次 Eval 必须记录：

- model
- agent version
- skill revision
- date
- result
- evidence

## 14. 分阶段实施

### Phase 0 — Baseline Freeze

目标：冻结 V1 行为，避免升级过程规则漂移。

工作：

1. 固化现有 8 个 behavior contracts。
2. 记录 d660eaa 基线。
3. 保存一次真实 Agent 人工评测结果。
4. 明确 backward compatibility。

验收：

- 当前 static validation 继续 PASS。
- 原有 8 个行为 Contract 不减少。

### Phase 1 — Core Model V2

目标：先升级理论核心，不做复杂 Harness。

工作：

1. 新建 normative v2 spec。
2. 重写 L0/L1/L2/L3。
3. Minimal Diff 改为 Minimal Sufficient Change。
4. 增加 Context Contract。
5. 增加 Human Approval Boundary。
6. 角色改成 capability-based。
7. 更新 SKILL 摘要。

验收：

- 任务等级不再依赖人类工时。
- L0 仍保持轻量。
- 高风险一行改动能自动升级。
- 低风险机械大改不会自动升级成 L3。

### Phase 2 — Durable State

目标：让 L2/L3 支持跨 session 续接。

工作：

1. 定义 state/resume contract。
2. 加 Resume behavior cases。
3. 定义 revision drift。
4. 定义 checkpoint 最小字段。

验收：

- 有 state 时不重复从头分析。
- workspace drift 能被识别。
- failed attempts 被保留。
- next_action 能被下一 session 消费。

### Phase 3 — Eval Harness

目标：从静态文本检查升级到行为回归。

工作：

1. eval fixture schema。
2. 现有 8 cases 结构化。
3. 新增 V2 cases。
4. 增加结果格式。
5. CI 继续跑 static validation。
6. Agent behavior eval 初期使用 manual trigger 或 nightly。

验收：

- 至少 16 个行为 Case。
- 能区分 static PASS 与 behavior PASS。
- 能记录 model / version / skill revision。
- 能比较同一 Case 历史结果。

### Phase 4 — Maintainer-quality Gate

目标：解决“tests pass 但维护者不会合并”。

新增 Review 维度：

- functional correctness
- repo conformance
- scope discipline
- architecture coherence
- state-source uniqueness
- validation evidence

关键 fixture：

> tests pass，但复制 canonical logic 或制造第二状态源。

Agent 必须判定 needs fix，而不是 merge-ready。

### Phase 5 — Parallelism Awareness

目标：让规范认识并行 Agent，但不造 Scheduler。

工作：

1. parallel safety decision。
2. shared-state-sensitive Case。
3. write-set / dependency 规则。
4. delegation contract。

验收：

- 可拆任务可以建议并行。
- 共享状态任务默认串行。
- 同文件高冲突任务不盲拆。

## 16. V2 心智模型

V1：

Task → classify → minimal diff → test → summary

V2：

Task  
→ Risk + Change Surface + Uncertainty  
→ Select Minimal Context  
→ Choose Lightest Safe Execution Mode  
→ Minimal Sufficient Change  
→ Observe Real Harness Feedback  
→ Checkpoint / Resume when needed  
→ Functional + Repository + Regression Evidence  
→ Maintainer-quality Review  
→ Evidence-based Summary

一句话：

> 不要把 AI 当成“更快的程序员”，而要把 Coding Agent 当成运行在工程 Harness 中、必须通过上下文、状态、工具反馈和可验证证据约束的执行主体。

## 17. V2 完成定义

V2 完成必须同时满足：

- [ ] 任务分级不再由人类工时主导。
- [ ] Minimal Sufficient Change 成为默认原则。
- [ ] Context Contract 已进入规范和 Skill。
- [ ] L2/L3 有 durable state / resume 规则。
- [ ] 高风险 gate 只阻止不可逆副作用。
- [ ] 角色定义不绑定厂商。
- [ ] tests pass 不再自动等于 merge-ready。
- [ ] 至少 16 个 behavior contracts。
- [ ] static eval 与 agent behavior eval 分离。
- [ ] 行为评测记录 model、version、Skill revision。
- [ ] 并行任务有 safety decision。
- [ ] 仓库没有演变成 orchestration platform。
- [ ] README、SKILL、normative spec、evals 不存在第二套互相冲突的概念体系。
