# Code Pact V2.2 大方向设计

- 文档状态：方向基线（待分阶段实施与验证）
- 目标版本：Code Pact V2.2
- 产品名称：Code Pact
- Skill 标识：`$code-pact`
- 仓库：`yeqiana/code-pact`
- 设计原则：通用入口、按需治理、证据闭环、人工掌握最终决策

## 1. 目标与定位

Code Pact 从“AI Coding 规范 Skill”升级为**通用 AI Coding 工作协议与执行治理框架**。

它不替代 Coding Agent、MCP Server、CI 或项目管理系统，而是统一回答：当前任务是什么；需要哪些上下文；应启用哪些工程机制；如何在授权范围内执行并验证；如何保存跨轮次状态和证据；如何证明目标完成以及谁接受剩余风险。

目标体验是：用户只表达目标，Code Pact 自动选择合适流程；简单任务保持轻量，复杂任务获得完整治理。

## 2. 产品边界与设计原则

### 2.1 做什么

- 统一任务入口与模式识别。
- 根据风险、变更范围、不确定性和持续时间选择工作流程。
- 动态加载适用的工程规则。
- 对复杂任务维护需求、问题、决策、评审轮次和验证证据。
- 对实施结果进行需求反向对账。
- 对风险接受、不可逆操作和外部发布保留明确的人类审批边界。
- 通过静态校验和真实 Agent 行为评测持续验证 Skill 本身。

### 2.2 不做什么

- 不自建 Agent Runtime、Scheduler、数据库或长期记忆服务。
- 不取代 Git、CI、测试框架、OpenSpec 或企业缺陷管理系统。
- 不要求每个任务创建方案、台账和检查清单。
- 不把所有任务升级成 L3，不要求每次评审固定执行相同数量的轮次。
- 不把脚本字段校验包装成 AI 判断正确性或业务验收通过。

### 2.3 五条原则

1. **一个入口，多种模式**：用户不必记忆复杂命令，明确模式也应得到尊重。
2. **机制按需启用**：只有复杂度、风险或持续性触发时，才创建持久化状态。
3. **原始目标不可被悄悄改写**：需求变化必须追加变更记录，不覆盖初始基线。
4. **证据高于自我声明**：计划不是结果、修复不是验证、测试通过不等于需求完整。
5. **人掌握最终决策**：Agent 可以评估和建议，但不能代替用户接受重大风险、批准破坏性动作或发布。

## 3. 统一入口与任务路由

统一入口：`$code-pact` / `/code-pact`。根据用户表达自动路由，必要时允许用户明确指定模式。

| 模式 | 典型请求 | 主要输出 | 默认权限 |
|---|---|---|---|
| Analyze | 分析项目、审计架构、梳理技术债 | 项目地图、事实与风险、证据和建议 | 只读 |
| Plan | 制定方案、评审设计、拆分任务 | 需求基线、决策记录、实施计划、验收标准 | 只读 |
| Implement | 实施方案、开发功能、重构 | 代码改动、影响分析、验证记录 | 授权范围内本地修改 |
| Debug | 排查问题、修复 Bug | 复现条件、根因证据链、修复与回归 | 先诊断，修改按授权 |
| Review | 评审方案、评审代码、多轮设计评审 | Finding 台账、轮次差异、风险处置 | 默认只读 |
| Verify | 测试、验收、检查是否遗漏 | 需求-改动-测试-证据矩阵 | 执行测试需满足环境与授权 |
| Release | 提交、打包、发布、部署 | 发布清单、版本和验证证据 | 外部写入/发布需授权 |

路由规则：

- 任务模式与 L0-L3 任务等级是两个维度。例如 Review 可能是 L1 快速审查，也可能是 L3 多轮架构评审。
- 用户明确指定模式时优先遵循；自然语言不明确时先检查仓库现状，再询问唯一会改变实施方案的关键问题。
- 任务执行过程中可以切换模式，但必须保留已有需求、问题和验证状态。
- 不因使用统一入口而强制创建文档；仅在多轮评审、长任务、跨会话恢复、复杂实施验收等场景启用持久化状态。

## 4. 八项工程机制与优先级

| 优先级 | 机制 | 解决的问题 | 落地方式 |
|---|---|---|---|
| P0 | 多轮 Review Lifecycle | 评审轮次混乱、遗漏、重复问题、最终状态不清 | 统一 Review Session 与追加式台账 |
| P0 | 需求可追溯与完成门禁 | 原始需求与实现、测试脱节 | REQ → Change → Validation → Evidence 双向追踪 |
| P0 | 根因优先调试 | 只修表面现象、根因靠猜测 | 假设、支持证据、反证、复现与修复验证 |
| P0 | 完成前独立验证 | AI 自己修改后自己宣布完成 | 独立复核、真实命令/结果、最终验收门禁 |
| P1 | 动态上下文加载 | 上下文过载、历史结论污染 | 按任务和影响范围加载规范、代码与历史证据 |
| P1 | Spec 生命周期协作 | 方案与代码漂移 | 需求基线、变更记录、实施状态和归档；兼容现有 OpenSpec |
| P1 | 真实 Agent 行为评测 | 静态规则通过但模型不遵守 | Harness-neutral Case、真实运行记录、跨版本回归 |
| P2 | Hooks 与跨 Harness 适配 | 不同 Coding Agent 执行边界不一致 | 适配器/能力检测；宿主不支持时明确降级，不伪造能力 |

这些机制不是每次全部启用。任务路由器根据任务等级、风险、共享状态和持续时间选择最小充分机制。

## 5. 核心能力：Review Lifecycle

### 5.1 触发条件

满足任一条件时启用持久化 Review Session：

- 用户要求多轮评审、持续评审直到满足标准。
- 设计/架构方案包含多个需求、多个模块或多个验收条件。
- 评审结果需要跨会话继续。
- 存在多个待处理问题、风险决策或多轮修复复审。
- 用户明确要求追踪遗漏、根因、风险接受和最终验收。

简单的单次代码 Review 仍使用 Quick/Standard 轻量模式，不强制创建台账。

### 5.2 单一事实源与目录约定

默认在目标项目中创建：

```text
.code-pact/
└── reviews/
    └── REV-YYYYMMDD-xxx/
        ├── review.json          # 唯一结构化状态源
        ├── rounds/
        │   ├── R01.md           # 每轮评审记录
        │   └── R02.md
        ├── evidence/            # 实际测试、日志、截图等证据
        └── final-report.md      # 从台账汇总的最终报告
```

若项目已有评审记录目录，优先遵循项目约定，不强行迁移。简单任务不创建该目录。不得把临时日志、未验证输出或无关产物写入评审目录。

### 5.3 核心实体

| 实体 | ID 示例 | 职责 | 关键约束 |
|---|---|---|---|
| Review Session | REV-20261110-001 | 管理一次完整评审生命周期 | 固定目标、范围、基线和状态 |
| Requirement | REQ-001 | 保存原始需求和验收标准 | ID 稳定；变更追加，不覆盖 |
| Finding | F-001 | 保存缺陷、风险、测试缺口或待确认事项 | 跨轮次复用 ID；重复项合并并保留历史 |
| Decision | DEC-001 | 保存修复、排除、延期或接受风险的决定 | 记录理由、决策人和时间 |
| Review Round | R01…Rn | 保存每轮检查范围、发现、复核和变化 | 轮次连续；历史不静默覆盖 |
| Validation | VAL-001 | 保存测试/构建/人工核验结果 | 记录命令、退出码、版本和证据 |
| Final | PASS 等 | 汇总最终验收结论 | 必须针对最新基线和最新轮次 |

### 5.4 评审轮次

1. **R0 Baseline**：冻结原始需求、验收条件、方案版本/哈希、Git HEAD、工作区状态和评审范围。
2. **R1 Initial Review**：独立检查需求完整性、设计合理性、可行性、风险和验证方案，建立 Finding 台账。
3. **R2 Challenge Review**：反向挑战上一轮结论，查遗漏、反例、根因误判、风险低估和新引入的问题。
4. **R3…Rn Fix & Regression Review**：按影响范围复核修复，检查回归；新问题加入台账，旧问题沿用原 ID。
5. **Final Review**：重新核对全部强制需求、所有 Finding 的最终处置、必要验证证据和最新代码/方案版本，生成最终报告。

不强制固定轮数；但多轮评审至少要有一次独立挑战复核。每轮必须有范围、基线版本、变化记录和结论。若基线发生漂移，旧证据不得直接沿用。

### 5.5 Finding 分类与状态

分类回答“这是什么”，状态回答“现在处理到哪一步”，二者不能混用。

分类：

- `confirmed_defect`：已有证据证明违反约定。
- `source_risk`：源码显示风险路径，但影响或触发条件尚待验证。
- `test_gap`：缺少足以证明行为的测试。
- `pending`：事实不足，尚不能判断。
- `excluded`：有反证证明不是有效问题或不在范围内。

状态：

- `open` → `investigating` → `fixed_pending_verification` → `verified_closed`
- 可转入 `accepted_risk`，但必须有用户明确批准的 Decision。
- 可转入 `rejected_with_evidence`，但必须保留反证。
- `blocked` 表示缺少权限、环境或证据，不能伪装成已解决。
- 已关闭问题再次出现时，使用原 Finding ID 重新打开，保留历史事件。

### 5.6 根因证据链

每个重要 Finding 至少记录：

1. 观察到的现象和复现条件。
2. 被违反的需求、接口契约、不变量或工程约定。
3. 从入口到异常结果的可达调用/数据/状态路径。
4. 根因假设及支持证据。
5. 主动寻找的反证与排除理由。
6. 根因状态：`unknown / hypothesis / likely / confirmed / not_applicable`。
7. 修复边界、修复证据和回归验证。

`likely` 或 `unknown` 不得写成“根因已确认”。没有复现也不等于问题不存在。对暂时无法确定根因的高影响问题，应保持 BLOCKED 或继续调查。

### 5.7 风险接受机制

- Agent 负责评估影响、概率、可利用性、缓解措施和剩余风险，并提出建议。
- **只有用户明确批准，才能把 Finding 标记为 `accepted_risk`。**
- 接受记录必须包含：Finding ID、接受理由、影响、发生概率、缓解措施、剩余风险、批准人、批准时间、复查日期或触发条件。
- 严重/高危、权限绕过、敏感信息泄露、数据丢失/破坏/不一致等风险默认不可通过普通接受流程放行；需要修复或进入单独的专项例外审批。
- `accepted_risk` 不等于修复完成，不得从报告中隐藏。
- `deferred` 不等于 `accepted_risk`；延期必须有负责人、期限和复查条件。

### 5.8 最终验收门禁

最终结论只允许：

| 结论 | 判定 |
|---|---|
| `PASS` | 所有强制需求有证据满足；必要验证通过；无未处置阻断问题和未批准风险 |
| `PASS_WITH_ACCEPTED_RISKS` | 强制需求和必要验证满足；仅剩经过用户明确批准、符合接受策略的风险 |
| `FAIL` | 存在明确未满足的强制需求、失败的必要验证或未解决的阻断缺陷 |
| `BLOCKED` | 缺少环境、权限、版本基线或必要证据，无法可靠判断 |

最终报告必须逐项列出：原始需求总数和状态；所有 Finding 的状态、根因和处置；新增、关闭、重开、接受及延期的问题；必要验证的命令、退出码、执行版本和证据；未覆盖范围；尚未批准的风险和决定。

不得由“最后一轮没有发现新问题”推导为“全部完成”。不得由测试通过推导为需求完整。最终验收必须回到原始需求基线。

## 6. 分层架构

| 层 | 职责 | 主要产物 |
|---|---|---|
| Entry & Router | 解析目标、识别模式和任务等级 | Task Mode / Task Level |
| Context Engine | 选择性加载项目规范、代码、调用方、历史证据 | Context Set |
| Workflow / Mechanism Registry | 按需选择 Review、TDD、Spec、Debug、Verify 等机制 | Workflow Plan |
| Lifecycle Ledger | 维护需求、Finding、Decision、Round、Validation | review.json |
| Evidence & Gate | 检查结构完整性、版本一致性和最终门禁 | Validation Report / Final |
| Harness Adapter | 将抽象能力映射到 Codex、Claude Code、Cursor、CLI、CI 等宿主 | Capability Map |

Skill 负责规范、路由和证据约定；本地脚本只负责可确定的结构/状态校验；宿主 Agent 和工程工具负责实际分析、修改、运行和观察。不得把静态脚本描述成自动理解业务或自动发现漏洞的扫描器。

## 7. 跨 Harness 兼容

- 核心规则保持厂商中立，不绑定某一模型或 IDE。
- 通过能力检测识别文件读写、终端、测试、Hooks、子 Agent、持久化状态和外部连接。
- 宿主不支持某项能力时，提供明确的人工/命令行降级方式；不能声称已执行。
- Hooks 只作为可选的生命周期增强，不作为核心正确性的唯一保障。
- 所有最终结论都必须能回溯到项目文件、命令输出、测试结果或明确的人类决定。

## 8. 分阶段实施路线

### Phase 0 — 方向与兼容基线

- 落地本方向文档。
- 审计现有 V2.1 Skill、规范、行为评测和测试门禁。
- 保留 V1 冻结基线、现有 20 个行为 Case、历史评测结果及用户未跟踪数据。
- 明确新增能力与现有 Context / State / Evaluation / Tool Safety Contract 的边界。

### Phase 1 — Review Lifecycle 最小闭环（P0）

- 新增 Review Lifecycle 规范、结构化台账模板和 JSON Schema。
- 实现无第三方依赖的确定性校验工具。
- 校验轮次连续、ID 唯一、状态迁移、需求证据、根因证据、风险接受审批和 Final 一致性。
- 将 Review Lifecycle 接入唯一规范源与 SKILL 快速入口。
- 增加多轮评审行为 Case 和反向测试。

### Phase 2 — 统一任务入口与按需路由（P0/P1）

- 将 Analyze / Plan / Implement / Debug / Review / Verify / Release 变成明确的任务模式。
- 区分任务模式与 L0-L3 等级。
- 明确每种模式的默认权限、输入、输出和升级条件。
- 小任务仍保持轻量，不强制创建 Review Session。

### Phase 3 — 实施与验收追溯（P1）

- 建立 REQ → Change → Test → Evidence 的双向映射。
- 将方案 MD 的验收条件转成可核对的需求条目。
- 实施后进行全量需求反向对账。
- 支持基线漂移检测、历史证据失效和跨会话续接。

### Phase 4 — Agent 行为评测（P1）

- 保留静态门禁与真实 Agent 行为评测的明确区分。
- 覆盖轮次乱序、遗漏需求、重复 Finding、根因误判、风险误接受、过期证据和最终结论错误。
- 记录模型、Agent Runtime、Skill revision、Case revision、运行时间和原始证据。
- 未实际运行的 Case 标记为未执行，不得推断通过。

### Phase 5 — Hooks / Harness 适配（P2）

- 对 Codex、Claude Code、Cursor 等宿主做能力映射。
- 只在宿主支持时启用 Hooks、子 Agent 和自动化生命周期事件。
- 先验证可移植核心，再增加厂商适配。
- 不建设自有 Agent Runtime、Scheduler 或数据库。

## 9. V2.2 完成定义

- [ ] 一个入口可识别七种任务模式，并与 L0-L3 分级解耦。
- [ ] 轻量任务不被强制创建持久化文档。
- [ ] 多轮评审有稳定 Review ID、REQ/Finding/Decision/Validation ID。
- [ ] R1…Rn 连续，历史问题跨轮次沿用 ID，重开不丢历史。
- [ ] 根因状态明确区分假设、可能和已确认，并保留支持证据与反证。
- [ ] 风险接受必须由用户明确批准，记录剩余风险和复查条件。
- [ ] 最终验收回到原始需求，核对最新方案/代码版本和全部必要证据。
- [ ] 静态校验能拒绝轮次乱序、证据缺失、非法状态迁移和虚假 PASS。
- [ ] 行为评测覆盖多轮遗漏、根因、风险接受和最终验收。
- [ ] 中英文 README、SKILL、唯一规范源和测试契约保持一致。
- [ ] 原有 V1/V2 能力、历史结果和用户工作区数据未被破坏。
- [ ] 不引入 Agent Runtime、Scheduler、数据库或不必要的第三方依赖。

## 10. 本轮实施边界

本方向文档是后续工作的统一设计基线，不代表全部能力已经实现。

首批实施范围限定为 Phase 1：Review Lifecycle 规范、结构化台账、确定性校验、Skill 接入和行为回归。其余任务模式和机制按路线逐步落地。每一阶段单独评审、测试和验收，禁止一次性把所有机制堆入入口文件。

## 11. 现有能力复用

- 继续以 `references/code-pact-execution-spec-v2.md` 为唯一 active normative source。
- 复用 Context Contract、State / Resume Contract、Evaluation Contract、Tool Safety Contract 和 Parallelism / Delegation Contract。
- 复用现有 20 个 V2 行为 Case、V1 冻结基线和真实 Agent 评测记录。
- Finding 分类沿用证据优先的代码评审术语；分类与生命周期状态分离。
- OpenSpec 继续作为可选规格管理工具，不在 Code Pact 内复制一套完整规格系统。
- 所有新增脚本只校验确定性约束，不宣称能够替代人工或 Agent 的语义评审。
